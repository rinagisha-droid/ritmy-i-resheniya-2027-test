# Первый этап платного доступа — «Магия каждого дня. 2027 г.»

**Статус:** структура базы и проверка прайса подготовлены; **живой вход, обработчик Prodamus и защита платного контента пока не включены**. Не обещать автоматическую выдачу до тестовой покупки.

## Подтверждённые правила продукта

- Один продукт: полный доступ к календарю на 2027 год, не подписка.
- 990 ₽ до **20 ноября 2026 включительно**.
- 1 590 ₽ с **21 по 30 ноября 2026 включительно**.
- 1 990 ₽ начиная с **1 декабря 2026**.
- Границы цены: **Asia/Yekaterinburg (UTC+05:00)**, сервер определяет актуальную цену.
- Оплаченный доступ открыт до **1 января 2028 00:00 в Уфе** (31 декабря 2027 включительно).
- Бесплатная версия/демонстрация остаётся публичной; платная версия должна физически храниться за проверкой доступа.

## Текущее состояние репозитория

- `index.html` — **публичный** полнофункциональный HTML на GitHub Pages. Пока он содержит код и материалы, простое скрытие блоков JavaScript-проверкой не является защитой.
- `landing.html` — публичная страница с тремя ступенями цен и тремя ссылками `payform.ru`, после поправки показывает утверждённые даты.
- `access/schema.sql` — проект структуры Supabase (цены, заказы, оплаченные права доступа, политики RLS). **Пока не применён** к реальной базе.
- Никакой пароль, секретный ключ Prodamus или Supabase `service_role` не должен храниться в HTML/публичном GitHub.

## Как должна пройти покупка

1. Покупатель на лендинге нажимает «Получить доступ».
2. Входит по email (одноразовая ссылка / код через Supabase Auth). Его email нужен, чтобы восстановить доступ на другом устройстве.
3. Защищённый сервер создаёт уникальный `order_id`, определяет **по серверному времени** актуальную цену и формирует персональный счёт/ссылку Prodamus с этим `order_id`.
4. Prodamus отправляет **серверное** уведомление об оплате на HTTPS webhook.
5. Обработчик проверяет **подпись и подлинность запроса**, номер заказа, ожидаемую сумму, валюту, магазин и окончательный статус. Повтор webhook не создаёт повторную покупку.
6. После подтверждения запись заказа становится `paid`, а отдельная запись выдаёт покупателю право читать платный календарь до 2028-01-01 00:00 (+05:00).
7. Покупатель открывает закрытую версию с любого своего устройства после входа. Сервер проверяет email-аккаунт и активное право доступа при каждом защищённом запросе.
8. При возврате средств/отзыве доступа право аннулируется. По окончании 2027 года доступ истекает автоматически.

**Нельзя** выдавать доступ по факту перехода на страницу «Оплата прошла» или по видимому в браузере `status=success`. Нужен проверенный webhook.

## Почему нельзя ограничиться GitHub Pages

GitHub Pages — статический публичный хостинг. Текущий `index.html` отдается посетителю целиком. Проверка даты в JS, локальный пароль в JS, шифр, ключ внутри HTML или закрытие репозитория **не создают** полноценную платную защиту уже опубликованного HTML.

**Для релиза:** GitHub Pages оставляем под лендинг и демоверсию. Полный платный функционал/платные данные переносим в защищённую часть приложения (например, приватное хранилище плюс Supabase Edge Functions, которые проверяют Auth и право доступа). Старые публичные материалы, ранее скопированные посетителями, технически нельзя отозвать.

Локальные планы, хранящиеся сейчас в браузере, автоматически не переедут с устройства на устройство. Для синхронизации понадобится отдельный проект миграции/хранения.

## Следующий этап подключения (после согласованного первого)

1. Подключить Supabase и создать проект. Секреты вводить **только в настройках Supabase**, не в сообщениях и не в репозитории.
2. Применить `access/schema.sql` в SQL Editor проекта. Проверить политики доступа и возможность восстановить вход по email.
3. Разработать две защищённые Edge Functions: `create-payment` (персональная ссылка) и `prodamus-webhook` (проверка подписи + активация); проверить действующий формат Prodamus в кабинете.
4. В кабинете Prodamus установить адрес уведомлений, убедиться, что доступны уведомления «Заказ оплачен», и протестировать **тестовую** оплату и повтор уведомления.
5. Убрать прямое использование общих ссылок из платной кнопки; не давать покупателю доступ до проверки его заказа.
6. Перенести платную часть календаря из публичного `index.html` в защищённую версию. Оставить демоверсию на GitHub Pages.
7. Пройти тесты: не оплачено, оплачено, повтор платежа, неверная подпись, возврат, другой браузер, истёкший срок, сохранение собственных дат.

## Что полезного было в присланном исходнике лендинга Ирины

В загруженном `view-source` HTML есть три переменные ссылки оплаты, переключение цены в браузере по дате и окно согласий перед оплатой. **В этом конкретном файле нет серверной проверки оплаты или личного кабинета**; текст про персональный пароль — заявление на странице, а не описание механизма. Нельзя выводить из этого файла, как защищён её фактический календарь.

У нас уже реализована смена цены в лендинге; она полезна как интерфейс, но **сервер обязан самостоятельно подтвердить цену** (браузерные дату и JavaScript можно изменить).

## Ограничения первого этапа

- Это **проект схемы**, пока не настоящая система лицензирования.
- Ни одной оплаты не проверяли, ни один email не авторизовали.
- Суммы, параметры динамических ссылок, webhook и секретный ключ требуют проверки по актуальному кабинету Prodamus перед подключением.
- Не отправлять покупателям ссылку на публичный `index.html` в качестве «защищённой платной версии».
